# Windows read-only monitoring setup (15-minute intervals)

The monitor is a **one-shot process** launched repeatedly by Windows Task Scheduler. You do not leave PyCharm or Anvil running. Your PC must be powered on; sleeping or shut down stops regular checks. A configured Windows scheduled task is **not** a cloud monitoring service.

## Install after pulling the branch

From the project root in PowerShell:

```powershell
git pull --ff-only
.\.venv\Scripts\python.exe -m pytest -q
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\run_monitor.ps1
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\install_monitor_task.ps1
```

Only the last command installs a scheduled job. Running `run_monitor.ps1` manually is a one-shot test. The scheduler repeats every 15 minutes for up to one year, with overlapping task launches ignored. The Python worker also protects its SQLite journal with an exclusive lock.

Runner: `scripts/run_monitor.ps1` sets the working directory to the repository root, uses the project's virtual environment and falls back to public `https://mainnet.base.org` if `BASE_RPC_URL` is absent. When using a private RPC provider, configure its endpoint for the scheduled user's environment rather than writing credentials into scripts, logs or Git. The public endpoint may rate-limit or fail.

Check:
```powershell
Get-ScheduledTask -TaskName "Lapidus Vault Systems - Read Only Monitor"
Get-Content .\data\monitor_status.json
Get-Content .\data\monitor_logs\$(Get-Date -Format yyyy-MM-dd).log -Tail 30
```

Stop or remove:
```powershell
Disable-ScheduledTask -TaskName "Lapidus Vault Systems - Read Only Monitor"
Unregister-ScheduledTask -TaskName "Lapidus Vault Systems - Read Only Monitor" -Confirm:$false
```

## Status, errors and alerts

Success and recommendation statuses are written atomically to `data/monitor_status.json`: `NO_REBALANCE_NEEDED`, `REBALANCE_REVIEW`. Failure writes `MONITOR_FAILED` with a sanitized error category, and the error is also logged in SQLite where possible. Run logs are under `data/monitor_logs/` and success observations under `data/lapidus.sqlite3`.

**This is not remote push notifications.** The status JSON is a file an external notifier can read; email/mobile alerts are a later integration. In particular, if the machine never runs the task, the status file becomes stale, so an independent heartbeat/staleness monitor will be required for stronger uptime claims.

Read-only monitoring now derives allocation drift directly from verified observations without rejecting unfunded wallets for missing ETH needed for hypothetical transaction execution. Live signing, automatic capital movement and execution authorization remain absent.
