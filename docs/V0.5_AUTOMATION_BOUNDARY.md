# LVS v0.5 — monitoring and automation boundary

**Automation begins now at the observation/planning level.** The new `monitor_once` is a one-shot, read-only monitoring program suitable for later invocation by Windows Task Scheduler or an always-on host. It uses verified API/RPC snapshot reads, planner rules, and a SQLite append-only observation table.

Example from the LVS PyCharm terminal:

```powershell
git pull --ff-only
.\.venv\Scripts\python.exe -m pytest -q
.\.venv\Scripts\python.exe -m lapidus_vaults.monitor_once --wallet 0x8685F85E3afcE79310658FB09d85BB98ecFc7EdE --allowlist data/paper_test_allowlist.json --drift-bps 500
```

On an empty wallet, expect `NO_REBALANCE_NEEDED`; the result is persisted into `data/lapidus.sqlite3`. On a funded wallet, the module may fail closed for insufficient ETH fee ceiling rather than issue a recommendation. The drift trigger is currently the maximum per-vault target discrepancy divided by total in-scope capital; it is *not* slippage, tracking error, or risk-adjusted portfolio drift.

Manual invocation is the only enabled operating mode. We have deliberately **not** created an unattended scheduled task or wallet-signer integration. Automatic signing/broadcasting is not enabled. A recurring OS task can later call the one-shot monitor, after adding failure alerting, duplicate-run locking, and config/endpoint hygiene.

For a **usable personally-funded MVP**, the desired staged controls are: read-only scheduled monitoring and alerts -> human-approved transaction execution -> receipts, post-state verification and journal -> optionally bounded unattended execution after extensive operational validation. No password/private key storage, no unattended wallet authorization at this stage.

## Package organization

For now, keep the existing command names working. A later incremental refactor can separate:
- `portfolio/`: holdings, allocator and targets
- `chain/`: read-only RPC and Morpho verification
- `transactions/`: safety and calldata candidates
- `operations/`: monitoring, journal and reconciliation
- `testing/`: strictly Anvil-only fork harnesses

Avoid moving everything at once. First establish tests for entry points and imports, then move one domain per change.

## Multi-vault coordination (supervised, not autonomous)

`execution_coordinator.supervise_candidates` consumes the existing unsigned candidate sequence and explicitly recorded receipt statuses. It makes at most one unconfirmed action eligible for **fresh manual preflight**. Pending transactions block advancement and must not be resent; failed or mismatched transactions halt and require a new portfolio snapshot and plan. A later confirmed action with an unresolved earlier action is rejected as contradictory.

This is a deterministic coordination policy, not an execution daemon: it does not yet connect journal observations to a persistent campaign, generate transactions for all vaults against live state, calculate independent Morpho V2 instant exit liquidity, or sign/broadcast. Those integrations remain required for a fully automated allocator. Start with supervised one-at-a-time execution before enabling any unattended mode.

## Package organization — incremental migration

New durable workflow state lives in `lapidus_vaults/operations/campaigns.py`. Keep the existing top-level modules and `python -m lapidus_vaults.<command>` entry points working; migrate by domain after test coverage, rather than moving all files in one risky change. The package layout is intended to become:

- `operations/`: campaign journal, lifecycle, receipt reconciliation, scheduler
- `portfolio/`: holdings, allocation and rebalancing
- `chain/`: RPC and Morpho adapters
- `execution/`: guarded quotes, candidate encoding and preflight
- Legacy top-level modules: compatibility entry points until integration tests pass

The campaign journal snapshots an existing unsigned plan and enforces sequential dependencies, transaction-hash binding, immutable terminal outcomes, and a one-active-campaign rule. It does not automatically attach to the local console, derive receipt statuses from RPC, or initiate transactions. `record_receipt_status` accepts caller-supplied statuses and **must not** be exposed as a public proof-of-success API; callers must first verify an exact matching transaction and receipt. Only receipt reconciliation performed against chain data is authoritative. A halted campaign does not cancel an already pending chain transaction.

## Verified-plan campaign builder

`operations/campaign_builder.py` creates an **unsigned, non-executable** persistent campaign from an existing `build_live_readonly_plan` result. It verifies the wallet, chain, plan freshness, vault allowlist, and per-action cap; planned withdrawals additionally run the existing pinned-block withdrawal quote/simulation. A failed simulation blocks campaign creation. A successful simulation is only evidence of liquidity at that observation, not a guarantee that funds remain immediately withdrawable when execution eventually occurs. Future actions still require fresh preflight and independent MetaMask authorization. It neither signs nor broadcasts transactions; no scheduler integration yet.
