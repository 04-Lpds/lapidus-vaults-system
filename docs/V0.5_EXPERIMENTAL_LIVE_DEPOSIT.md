# LVS first manual MetaMask deposit — experimental live path

The existing local console now includes a **manual** single-vault approval/deposit UI, capped at 10 USDC per operation. It uses only the *first* vault in the explicit allowlist. It does **not** execute the portfolio allocation plan, rebalance autonomously, or guarantee a safe investment.

## Local launch

```powershell
git pull --ff-only
.\.venv\Scripts\python.exe -m pytest -q
.\.venv\Scripts\python.exe -m lapidus_vaults.local_console --wallet 0x8685F85E3afcE79310658FB09d85BB98ecFc7EdE --allowlist data/paper_test_allowlist.json
```

Open http://127.0.0.1:8765/ and connect MetaMask to the same address on Base chain 8453. The browser sends no private keys to LVS. Start with a very small USDC amount.

1. **Check live deposit/approval**: backend verifies Base, explicit vault and native USDC, amount <=10 USDC, wallet USDC and ETH reserve, current allowance, per-action gas estimate, fresh block and quote expiration. If allowance is insufficient and zero, the next **separate** MetaMask transaction is an exact-amount ERC20 `approve(vault,amount)`.
2. **Review & authorize**: after a second live backend check LVS persists the exact transaction in `live_deposit_authorizations`. Only the visible MetaMask button issues `eth_sendTransaction`. Carefully confirm network, recipient, method, amount and gas in MetaMask. Do not approve a different contract.
3. Receipt matching compares the transaction sender, recipient, exact calldata, Base chain ID, value, status and block-to-block USDC/share changes, journaling checks in `live_deposit_receipt_checks`. It can be pending; use **Recheck submitted transaction** without resubmitting.
4. Once approval is confirmed, start **a new quote** for the deposit step. Approval and deposit are **never sent automatically as a sequence**. A deposit requires `previewDeposit` returning positive shares, a current pinned `eth_call` from the wallet succeeding, and a fresh gas estimate.

## Known limits — read before authorizing

* This integration is **experimental and has not yet been tested end-to-end with real funds**. Only offline Python CI and earlier local Anvil fork tests have passed. In particular, the *browser handoff itself* has not been proven on mainnet.
* A successful `eth_call` demonstrates that an operation appears possible at the observed state, **not** that vault deposits/withdrawals will always be available or that adapter capacity is safe. The system does not yet independently evaluate Morpho Vault V2 adapter caps, gates, queues, or strategy risk. There is no withdrawal button in this slice.
* Transaction fees can exceed quoted assumptions, and ETH gas reserve assumptions are policy estimates. Never treat a quote as a guarantee. Quote expires after ~20 seconds; review and submit only fresh quotes.
* Approvals authorize the selected vault to spend the quoted amount of USDC. A UI approval is **not** a USDC deposit. A separate deposit requires another MetaMask confirmation. Revoking an existing approval is a separate action not offered here.
* Receipt checks are **block-level**, not isolated transaction-level event proof. If unrelated transactions occur in the same block, deltas may be misleading. A successful result is not a full financial reconciliation.
* Each local server restart loses in-memory consumed-quote IDs; submitted transactions remain on-chain. Track hashes in MetaMask and the SQLite journal. If any step fails, **stop and inspect wallet activity before retrying**.
* This is NOT full automatic execution, production monitoring of pending transaction recovery, a production security audit or an investment recommendation.

Do not send amounts that exceed what you are comfortable losing. First use a dedicated low-balance wallet; never paste seed phrases/private keys into the application.
