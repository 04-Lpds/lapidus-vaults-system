# v0.5 Saved Manifest Freshness Checks (read-only)

This module checks that a saved SQLite proposal still has the correct SHA-256 content hash, sender, Base chain ID, exact allowlist, action-order dependencies, capped amounts and supported ABI calldata. It rejects future observations and labels proposals more than 20 Base blocks old as `STALE_REPLAN_REQUIRED`.

```powershell
git pull --ff-only
.\.venv\Scripts\python.exe -m pytest -q
.\.venv\Scripts\python.exe -m lapidus_vaults.manifest_preflight --manifest-id 1 --wallet 0x8685F85E3afcE79310658FB09d85BB98ecFc7EdE --allowlist data/paper_test_allowlist.json
```

Since saved manifest #1 was observed earlier, it is expected to be **stale**, not valid for execution. This is desirable: saved plans are not evergreen permission to move funds. To inspect a fresh empty plan, rerun `transaction_review`, note the new ID and immediately call `manifest_preflight`.

The optional `eth_call` check only simulates each vault call **independently** against the current block. It does not apply previous withdrawals or approvals; a deposit might revert even when the complete transaction sequence could succeed. No live EIP-1559 envelope, nonce, signing, transaction broadcast, adapter-capacity proof, sequential simulation or authorization exists. Even `REVIEW_ONLY_NOT_EXECUTABLE` does not grant permission to execute.

The next milestone is a stateful fork simulation of saved manifest candidates and transaction-to-journal reconciliation, followed by a manual wallet authorization design.
