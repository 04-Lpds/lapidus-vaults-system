# LVS v0.4-gamma — read-only static transaction preflight

Gamma builds on the existing beta wallet-aware planner and pinned-block RPC verification. It does **not** replace the beta indicative plan, nor does it enable execution.

## Windows PowerShell

After fetching this feature branch and installing the project in the virtual environment:

```powershell
$env:BASE_RPC_URL = "https://mainnet.base.org"
.\.venv\Scripts\python.exe -m lapidus_vaults.preflight --wallet 0x8685F85E3afcE79310658FB09d85BB98ecFc7EdE --allowlist data/paper_test_allowlist.json
.\.venv\Scripts\python.exe -m pytest -q
```

The allowlist remains a manually selected research list, not an authorization to invest.

## Checks

Reads use one pinned Base block after existing API/RPC verification. For each nonzero indicative delta:

- Deposit: current native USDC, USDC allowance to the vault, vault `maxDeposit(wallet)`, `previewDeposit(assets)`, and standalone `eth_call` of `deposit(assets,wallet)` from the wallet.
- Withdrawal: `maxWithdraw(wallet)`, `previewWithdraw(assets)`, observed shares, and standalone `eth_call` of `withdraw(assets,wallet,wallet)`.
- Wallet ETH must exceed a default **0.002 ETH reserve floor**. This number is not an estimated transaction fee.

`STATIC_PASS` means only that individual pinned-block checks succeeded; `BLOCKED` means that at least one check failed; `NO_ACTION` indicates a zero delta. No spend permission is granted, and the process has no signer or broadcasting support.

## Critical limitations and next increment

- Static calls assume the current state, **not the state after other planned actions**. For example, if the planner expects withdrawals to fund deposits, those deposits are blocked until wallet USDC is actually present. No cross-action accounting is simulated.
- The ETH reserve is a conservative heuristic, not `eth_estimateGas` multiplied by a fee quote. Gas units, EIP-1559 prices, and buffers need an independent follow-up implementation.
- Vault V2 withdrawal queues, liquidity constraints, different deposit/withdraw execution paths, fee state, caps, and router requirements may make ERC-4626 direct calls inappropriate. Explicit validation against deployed vault implementations is required.
- No sequential fork simulation, state overrides, calldata package for signing, receipt monitoring, slippage-protected execution, or live capital authorization.
- A successful `eth_call` does not guarantee inclusion or future success, even for one action.
- For an unfunded wallet with no rebalance deltas, the result is `NO_ACTION`. This **does not mean the account is funded or execution-ready**.

Keep this branch in draft until actual Base RPC behavior, especially the two selected Vault V2 contracts, is verified and local tests pass.
