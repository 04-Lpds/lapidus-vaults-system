# LVS v0.3-gamma — Research utilities

This is an **additive** read-only development increment. It deliberately adds a separate
Python module instead of editing `cli.py` or the existing SQLite schema, because some
local v0.3 previews may have different historical portfolio table names.

Run from the existing PyCharm project root, with its existing Python environment.

## 1. Full shared-market report (offline)

```powershell
.\.venv\Scripts\python.exe -m lapidus_vaults.risk_research overlap --capital-usdc 200 --allowlist data/paper_test_allowlist.json
```

Uses latest saved `exposure_snapshots` and `exposure_market_positions`, recreating
v0.2's **capped equal-weight** paper allocation from the allowlist. Prints **every
active shared market**, not merely those that exceed a warning threshold, with the
estimated USDC supplied by each vault and their share of that shared exposure.

The command does not change your existing saved paper plans, and makes no network calls.
It is not an audit of the historical allocations in older SQLite tables. The amounts
are estimates based on saved vault positions; they are not actual wallet investments.
Unknown/incomplete or unreconciled exposure snapshots cause a failure.

## 2. Broader candidate discovery (live API)

```powershell
.\.venv\Scripts\python.exe -m lapidus_vaults.risk_research candidates --universe-limit 200 --inspect-limit 20 --top 15
```

- Discovers up to 200 **listed** Base USDC Vault V2s (cursor-paginated).
- Samples up to 20 entries *spread across their sorted addresses*, avoiding the
  naive first-20-only problem. This is a **sample**, not the best 20 of all vaults.
- For each sampled vault, fetches state, configuration, and 7-day APY (up to **3 API
  requests per inspected vault**), applies the existing mechanical `assess_vault`
  checks, and sorts the observation queue by preliminary status then total assets.
- Appends inspected results in `research_candidates` in the LVS SQLite file.

**Limitations:** Can miss good candidates. The public directory is listing-gated.
High TVL, high APY, or a mechanical pass is not sufficient due diligence. Results
are not investment recommendations, and public API rate limits apply. Future
iterations should support fuller universe coverage, batching/caching, historical
observations, rigorous eligibility policies, and human approval.

## 3. Underlying market risk context (live API)

After you have saved `exposures` for one or more vaults:

```powershell
.\.venv\Scripts\python.exe -m lapidus_vaults.risk_research market-risk --vault 0x050cE30b927Da55177A4914EC73480238BAD56f0 --vault 0x1e9e47583f15D45a10Df48c0b1846E0492c795D7
```

- Deduplicates market IDs across the latest saved vault exposure snapshots.
- Queries Morpho's documented REST endpoints for immutable market configuration,
  indexed state, and separate market/public-allocator liquidity observations.
- Shows LLTV, supply, borrow, simple utilization (borrow/supply), unborrowed supply,
  oracle address, and IRM address. The ratio is a **snapshot proxy**, not necessarily
  the precise on-chain accrued utilization at a common block.
- Writes `research_market_states` with raw API responses, block reference (when
  provided), and missing-liquidity reasons. Market config and state must be complete
  before saving; missing separate liquidity responses are clearly marked.
- Doesn't sum Public Allocator liquidity with cash. Indexer freshness and executable
  withdrawal capacity have **not** been verified via RPC.

## 4. Quick verification

```powershell
.\.venv\Scripts\python.exe -m pytest -q
.\.venv\Scripts\python.exe -m lapidus_vaults.risk_research --help
```

The reference offline suite for the v0.3-beta ZIP + alpha/beta patches + this increment
is **65 passing tests** (50 existing plus 15 new). A different local branch may have
a different number; the criterion is that **all tests pass**.

Keep DB Browser closed while running tests and while writing research observations,
or at least ensure it has no open write transaction. SQLite is fine with concurrent
readers, but concurrent writers can lock the database.

No wallets, signer, approvals, transfers or transactions are implemented.
